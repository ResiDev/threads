==== overview
How the model works out its state
the code as it stands

The model has two kinds of state. Whose move a conversation is, and what waits for the agent,
are worked out from the messages each time something asks, and never stored (#1, #2). What you
have read, walked and accepted is kept in <id>.seen beside the review, under keys the model
makes (#3, then the keys in #4 and #5). Each thread answers one question with a tour you walk
with L and H.

==== #1 whole
#1  Whose move a conversation is  how it works                                             ✓ 0/4

Whose move it is comes from the last message, every time something asks. If your message is
last, it is the agent's move. If the agent's is last and you have said something in that
conversation, it is yours. If only the agent has spoken, or the thread is closed, it is nobody's
move. None of this is stored.

A conversation is either a thread's own messages (#12) or the messages of one of its steps
(#12.3). Each conversation has its own move. When you reply in a step, that step becomes the
agent's move and the thread's own conversation does not change.

A worked case, which I ran in a scratch repository. Thread 1's introduction is the agent's, and
it carries a tour of two steps. At first #1, #1.1 and #1.2 are all nobody's move. You reply in
step 1, and then:

- #1 still holds only the agent's introduction: nobody's move;
- #1.1 holds your reply: the agent's move;
- #1.2 has no messages: nobody's move.

Once the agent answers in #1.1, it is your move there.

All of the rule is in one function:

lua/thread/model/thread.lua:134
 134  function M.move(c)
 135    local last = c.messages[#c.messages]
 136    if not last or M.closed(c.thread) then
 137      return nil
 138    elseif last.from == 'you' then
 139      return 'agent'
 140    end
 141    for _, m in ipairs(c.messages) do
 142      if m.from == 'you' then
 143        return 'you'
 144      end
 145    end
 146    return nil
 147  end

#2  What waits for the agent  how it works                                                 ✓ 0/6

thread.waiting(r) decides it, and nothing else does: in an open review, every conversation whose
move is the agent's. No list of waiting conversations is stored. show.lua calls it for each open
review, and sending a message calls it too, to decide whether the message joins the round still
waiting or starts a new one.

So what waits changes only when someone adds a message or a status changes. Reading, walking and
accepting never affect it. An answer you have not read yet is still your move, not the agent's.

           32h ago  ●  Why does show.lua skip closed reviews, rather than list them last?

△  Because nothing in a closed review can wait for the agent, so listing one
   last would always show 0 waiting. thread.waiting returns an empty list
   for any review that is not open, and show.lua prints what it returns. Its
   own branch for closed adds two small things. A closed review is not
   counted among the open ones, and naming one prints that it is closed
   instead of an empty header.

   Closing a review is you saying you are done with it, the way closing a
   thread makes all its conversations nobody's move (#1.3). The one case
   that looks like lost work is a question you asked before closing the
   review, with no answer yet. Closing withdrew it. Anything you write after
   closing does reach the agent, because send opens the review again before
   it does anything else.

   The worked case is in tests/skill_spec.lua. A closed review shut has one
   thread holding only your message. show.lua lists nothing from it and
   counts one open review, the other one in the test. show.lua shut prints
   review shut is closed: nothing in it waits.

   I'd keep it. If an unanswered question should not slip by when you close
   a review, the close itself is the place to catch it. When stage 6 builds
   that action, it can say how many questions have no answer before it
   closes. That one is your call.

#5  Accepted follows the code  how it works                                                ✓ 0/7

Accepting a chunk stores a key made from its code as it is now, under its thread. When the code
changes, the key changes, and the chunk is back to accept. On a hunk of the review's diff, the
key is the whole hunk's. On plain code, it covers the chunk's own lines, and a chunk with no
lines is one line.

Two cases I ran in scratch repositories, each a check below:

- A diff that changes lines 3 and 4, one hunk. Accepting a chunk on line 3 also accepts one on
  line 4, since both have the key h911204fe4c47ec2b. Editing line 4 again makes line 3's chunk
  no longer accepted.
- Plain code, function f(), with a one-line chunk and a three-line chunk on it, both accepted.
  After the body changes, the three-line chunk is back to accept and the one-line chunk is still
  accepted.
