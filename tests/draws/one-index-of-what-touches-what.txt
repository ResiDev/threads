+ touch.index(r)  function and its table                        inline   split   side   as it is
Each thread's, tour's, step's, group's and contract's chunks and files, and which
contracts each thread, tour and group touches, worked out once.

+ ---@class thread.Touches
+ ---@field chunks table<thread.Owner, thread.Chunk[]>
+ ---@field files table<thread.Owner, table<string, true>>
+ ---@field contracts table<thread.Owner, thread.Contract[]>  a thread's, a tour's or a group's…
+ ---@field touched table<thread.Contract, table<thread.Owner, true>>  the threads, tours and g…
+ 
+ --- A review's index.
+ ---@param r thread.Review
+ ---@return thread.Touches
+ function M.index(r)

touch.index(r) returns a thread.Touches: four tables, each keyed by the table that owns
the chunks, not by an id.

field     │ keyed by                             │ holds
──────────┼──────────────────────────────────────┼──────────────────────────────────────
chunks    │ thread, tour, step, contract, group… │ its chunks, as written
files     │ the same                             │ the set of their files
contracts │ thread, tour or group                │ the contracts its chunks overlap, in…
touched   │ contract                             │ the threads, tours and groups that o…

touch.NONE stands for the threads in no group, so T.chunks[g.group or touch.NONE] reads
any review.grouped(r) entry.

Worked case: thread 1 has its own chunk on a.lua:1 and a tour whose steps are on a.lua:3
and on no line; contract end uses a.lua:3. Then T.files[t] is { ['a.lua'] = true },
T.files[step2] is {}, T.contracts[t] is { end }, and T.touched[end] holds the thread,
its tour and its group (the test in #step:7).

What to watch: keys are table identities, so a Touches answers only for the very r it
was built from. Read the review again and every lookup is nil (#note:3). And chunks
count as written, not as found in the code, unlike thread.chunks (#note:1).

+ touch.related(T, owner)  function                             inline   split   side   as it is
What is on the other side of an owner: a contract's threads, tours and groups, or a
thread's, tour's or group's contracts.

+ function M.related(T, owner)

It returns a set, keyed by owner tables, or nil. A contract gets T.touched[c] itself,
not a copy: a caller that writes to it changes the index. A thread, tour or group gets a
fresh set of its contracts. A step, or a table the index does not know, gets nil.

Worked case: with the cursor on contract end from touch.index(r)'s example, related
gives { [thread] = true, [tour] = true, [group] = true }, and the screen bars those
rows. On the thread, it gives { [end] = true }. On a step, nil: no bar anywhere
(#note:2).

+ side.owner(p)  function                                       inline   split   side   as it is
The table the index knows a drawn part by.

+ function M.owner(p)

It maps a part's kind to its owner: contract to p.contract, group to p.group.group or
touch.NONE, thread, tour and step to theirs; anything else to nil.

It goes by kind, not by which fields are set. That matters because draw.within fills
thread and tour into every part drawn inside a thread or a tour: a message part inside a
tour has p.tour set, but its kind is message, so it owns nothing.
